### 2.1 The protocol every page states (the pages carry the same rules)

- **One request open at a time per session**, taken in the order the page lists, with a standing request "VP": if
  nothing is open, reply in one line ("idle"). A request names its model and effort. A finished request is closed by the
  coordinator, who moves it to the page's log as one line and deletes its reply. Never leave a request queued behind a
  finished one.
- **Parts.** A request is cut into parts of at most 15 minutes, answered one by one ("part n of m"). After a restart a
  session resumes from its last reply, never from the start. Long runs go in the background (`nohup`, logged) with their
  build caches kept, so a rerun resumes; a restart that kills a timed run is the usual failure. A session does not
  re-read a log it has already summarized. Timed runs take under about 30 seconds each. Builds use `CARGO_INCREMENTAL=0
  CARGO_BUILD_JOBS=2`, and each worktree its own `CARGO_TARGET_DIR` (A29's timing run died twice, silently, on a shared one).
- **`df -h /` on the first line of every reply.** The disk floor is 15 GB, kept only to prevent container restarts: a
  session under it that is not restarting need not clear disk (the user, 2026-11-23). Ask for a clear, of the session's
  own regenerable build output only, after a restart or a run killed for space.
- **Never Haiku for the work.** A session's own coordinating role (reading the page, delegating, replying) may run on
  Haiku; the work runs on the model the request names (section 3). Wake-up messages name no model and run on the session's
  default.
- **Push only `vm/*` branches, never `main`.** Before a push, `scripts/quick.sh --extended` and the lints pass on the
  pushed sha; never the full gate, which the Mac runs before `main` (the user, 2026-11-23: "Agents should test their
  changes but not a full gate"). A cloud session whose container restarts may push an untested head to `vm/wip-<task>`
  only (the user, 2026-11-24: "Allow vm/wip-*"); the Mac tests that sha and the session pushes the same sha to the task
  branch after a pass.
- **Fixtures are written on macOS.** A state fixture whose bytes hold a libm result is compared to the bit on every OS;
  one regenerated on a cloud Linux box failed CI (`spectral_window`, 1 ulp). A cloud session pushes with the named
  fixture tests as its only failures and the Mac writes the fixtures at the merge. Bit-exact-by-design kinds (ddsketch,
  tdigest) are tagged linux and may be written anywhere.
- **Page size.** The page stays under 10 KB, a reply under 3 KB; both sides republish the whole page after reading it
  live and keep the other side's section. The coordinator edits Requests and the Log, the session edits Replies.
- **Permission refusals.** A session's own permission classifier sometimes refuses a `git commit` or a push (A on
  2026-11-22 and 11-24, C on 11-22, D on 11-23). The coordinator does not work around it or push the branch for the
  session: it tells the user, who answers in the session ("Allow ...") and, if the user wants, says so to the coordinator.
- **Questions of rule.** A session that asks "my user" or "the coordinator" about a rule the user already gave is
  answered by the coordinator, from the rule.

   Read only what changed since the last check: compare the branch tips and each page's update time with the log, and
   open a page or a reply only when its tip or time moved. Re-reading every page whole each time burned tokens in the
   long exchange of 2026-11-24, and the user paused the plan for tokens.
3. Answer every question in the same check, stating the model and effort for anything new. Review a part's claims against

4. Nudge a session that has been silent for over an hour on an open request, once, by message with no model named. Do not

5. Close a finished request, record its final in the log, open the next one only if the road allows it.
6. The check itself is a session-local timer (`CronCreate` or the host's scheduler): it dies with the session, so a new

## 3. Which model runs which work

The user's rules: "Run future tasks on medium where appropriate and choose high where needed" (2026-11-07) and "We want
tasks to run on models that are efficient without compromising quality" (2026-11-21, when the weekly Opus limit blocked
two studies). Pass `model` and `effort` on every agent spawn and every cloud request. Never Haiku for work.

| work | model and effort |
|---|---|
| New math, a model build in `rheon-core`, a saved-state layout (rule 5), a correctness bug of unknown cause, a first-principles derivation | Opus 5.5, high; medium only where the design is already fixed |
| Mechanical edits, a wave merge, moving test pins, regenerating fixtures, applying budgets, harness and CI fixes, a doc stage to an existing pattern, an oracle-checked study that follows an earlier template | Sonnet 5.5; medium for mechanical work, high where a derivation must be checked |
| A design check, an oracle search, the right answer for an output that moves by more than 5 ulps, a review the user asks for | Fable: high for the Rust model core and the Polars and Arrow integration, medium for the Python package, bindings, scripts, tests and CI (the user, 2026-11-20) |
| A cloud session's own coordinating role | Haiku is allowed (the user, 2026-11-22: "All sessions are allowed to use haiku as the coordinator just not for work"); the work runs on the named model |

Under the pause, prefer Sonnet for any mechanical step that remains (the merge, the fixtures, this handoff). When a weekly limit blocks a model, a session stands
by or the work moves to Sonnet with the reason said in one line; do not silently downgrade a derivation. Do not keep a
long-lived worker waiting on CI: a worker ends at `quick.sh --extended` and the lints and reports, and the coordinator
reads CI. Actions runners queued some pushes for over three hours on 2026-11-24, and a parked worker burns a slot and its
tokens. The lesson of the day, which ended with the pause for tokens: spend them on work, not on waiting or re-reading.
A worker's final report is short, an exchange check reads only what changed (section 2.3), and a mechanical step goes to
Sonnet. Fable reviews start only when the user triggers them (PLAN 546's amendment); another agent reviews meanwhile.

## 4. How a wave goes, in the order the coordinator did it

CLAUDE.md and `AGENT-WORKFLOW.md` give the rules. The sequence in practice, with what they leave out:

1. Branches finish at `quick.sh --extended` plus the lints and are pushed as `vm/*` (cloud) or stay as local branches (Mac).
2. While the last push's workflows still run, fold each branch that becomes final into the waiting wave on one branch, one
   `--no-ff` merge each so a CI failure can be traced; one full gate and one push when CI clears (the user, 2026-11-23:
   "minimize the number of ci by merging waves until the running ci is done"). The next push waits for every workflow of
   the previous push to finish.
3. A merge worker (Sonnet, high) regenerates every generated file that conflicts once (fixtures on macOS, goldens, the API
   snapshot, oracle hashes with `oracles.py rerun`), reconciles `WINDOWS_VERSION` when two branches stepped it, and adds
   the README index row of each new record.
4. The API review (PLAN 580), then `scripts/gate.sh --extended` on the exact sha, read as `GATE EXIT 0` in its own call,
   then the push, then `scripts/ci_status.py <sha> --repo rheon-dev/rheon` on every workflow of the previous push.
5. Budgets: a case over its budget needs its cause found before any raise; the first count of a new bench case comes from
   CI's Linux Valgrind, and `scripts/budgets.py apply` writes it. W13's 14 over-budget
   cases were each a real per-row cost added by a review fix, found only by counting instructions per merge under
   Valgrind; find the cause before raising a budget.
6. After the push, clear caches (`scripts/clear_caches.sh --worktrees`) and give back merged slots.

## 7. Lessons not written down elsewhere

- A review fix that changes a per-row path is the usual cause of a budget going over by 2 to 6%: W13's 14 cases over budget
  came from ten merges, each small. Time the per-row cost of a review fix on arm64 before merging it. The fixes that recovered the cost gated the new check,
  made it lazy or moved the rare path out of line (`#[cold]`).
- A test tolerance set at the maximum seen against a third-party library on one OS fails on another OS when that library is
  inexact there (scipy's special functions, the ddsketch package on Windows). Hold rheon to an exact reference (mpmath at
  50 to 160 digits) and keep the library as a second opinion at its own bound.
- A recovery test for an overflow needs a tail derived from the decay (about 2,012 half-lives for the fifth moment of
  `ewm_moments`), not a fixed row count.
- When a worker's test fails on a degenerate case, check the realistic case before changing the model (PLAN 550's rule).
- A page can be many hours stale (the pages were frozen from about 19:40 UTC on 2026-11-24 by the publish limit); read the
  session's branch before believing its page.
